# First experimental FLAC rip — isolated Unraid staging

**Stage:** prototype; explicit, manual rip only. This is NOT a validated archival workflow.

## Prerequisites

- The newest OSCAR image contains Debian Trixie packaged cyanrip, libdiscid and flac.
- Your actual optical drive is visible as a permitted `/dev/srN` device inside the container, and OSCAR sees a stable udev identity.
- The drive's **measured** read offset is entered and saved in OSCAR settings (blank/unknown offsets are intentionally rejected).
- Only an isolated scratch share is mounted writable: **host** `/mnt/user/ai-workspace`, **container** `/staging`.
- The OSCAR web UI has **no built-in login**. Restrict network access to your trusted LAN/reverse proxy. Experimental start requires a separate token as well.

## Portainer additions to the EXISTING stack

Review and merge these snippets into your current stack; do not replace your working mounts, permissions or env flags:

    services:
      oscar:
        image: ghcr.io/sin7ek/oscar:main
        environment:
          OSCAR_ENABLE_RIPPING: "1"
          OSCAR_RIP_ROOT: /staging
          OSCAR_RIP_TOKEN: "REPLACE_WITH_A_RANDOM_SECRET_OF_AT_LEAST_24_CHARACTERS"
        volumes:
          - /mnt/user/ai-workspace:/staging:rw
        devices:
          - /dev/srN:/dev/srN:r

Replace `srN` with the **actual** source block device discovered by OSCAR, and repeat a device mapping only for additional drives you explicitly want to test. If `/dev/srN` changes across reboots, update the mapping; OSCAR checks the current stable identity before starting. The GUI label `/dev1` is not necessarily a Linux device path.

Do **not** mount any existing music collection writable; no Docker socket, privileged mode, archive write access or deletion rights are needed. Keep `/config` persistent for existing settings and queues. Check that the container's non-root `oscar` user can write to `/staging` and read `/dev/srN` (Unraid ACLs and device group permissions may need a deliberate adjustment). Never expose the token in GitHub commits.

**Important:** the current normal OSCAR image uses a non-root user and the old preview stack uses a localhost-only published port. Retain these safeguards. The new build never changes them automatically.

## Browser workflow

1. Pull the new main image **only after the GitHub Actions publication completes successfully**, then redeploy the modified stack.
2. Insert a known test CD; click **Check inserted discs**.
3. Click **Test rip to staging (experimental)** for the correct drive.
4. Enter the secret token (not saved in browser storage). Inspect the displayed device, offset and number of tracks; explicitly confirm.
5. OSCAR launches cyanrip in a background thread. It always creates a new `/staging/oscar-<random-id>/` directory; existing folders are never reused.
6. The UI polls the job status. It should finish at `needs_verification` or `failed`, not at `verified`.
7. On Unraid inspect `/mnt/user/ai-workspace/oscar-<id>/` and the ripper's `audio/` subdirectory.

Every job stores:
- `plan.json`: device, MusicBrainz Disc ID, offset, parameters and track count.
- `state.json`: job status and file SHA-256 hashes (on success).
- `cyanrip-console.log`: captured console output (including diagnostics).
- `audio/`: FLAC and CUE/riplog output generated by cyanrip, as supported by the installed version.

The command is fixed: cyanrip uses the chosen drive and offset, FLAC, paranoia defaults, and no automatic MusicBrainz tagging, cover art, AcoustID or ReplayGain. It explicitly disables automatic deemphasis (`-W`), leaving preemphasis evaluation to a future archival decision. It does not enable eject (`-Q`) or risky overreading (`-O`). cyanrip's own AccurateRip lookup remains at its default; **OSCAR does not independently verify the evidence yet**.

## Scope and limitations

- Single job per enabled drive per running OSCAR process. This stage is not a multi-process locking system; use one OSCAR container/worker.
- Jobs run in threads, with a three-hour subprocess timeout. Container termination may interrupt extraction, leaving partial files. Those are intentionally not erased; old running state is reported as `interrupted` after restart.
- Logfile names and actual CUE contents are determined by cyanrip. OSCAR does not yet prove CUE integrity, FLAC decode, AccurateRip v1/v2 or CTDB status.
- File hashes detect later byte changes but **do not establish an accurate rip**. No automatic publishing, deletion, renaming or tagging of archive files exists.
- There is no stop/cancel button or job catalogue yet; retain staging output for manual review.
- Running with `OSCAR_ENABLE_RIPPING=0` or missing variable blocks all rip starts. Requests also require an explicit token and confirmation phrase.
- For a real archival collection, choose one known test disc and validate its reports before progressing.

## Manual acceptance check

- Record optical drive make/model/firmware, measured offset and Disc ID.
- Check FLAC track count, listening playback, CUE references and console log.
- Inspect cyanrip's AccurateRip lines; do not infer verification solely from process exit code.
- Re-run on a different **new** job ID and compare decoded PCM, not merely FLAC file hashes (metadata can differ).
- Only then plan independent AccurateRip/CTDB parsing and safe publication.

**Cleanup:** the sandbox share is intentionally disposable, but OSCAR does not delete it. Only manually remove a specific test-job folder after verifying you need no evidence from it.
